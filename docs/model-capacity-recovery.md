# 模型资源等待与崩溃恢复

本轮修复两个可重复触发的问题：短请求会把共用 Redis 模型槽键的 TTL 改短，导致仍存活的较长租约提前消失；Worker 遇到 `MODEL_BUSY` 时按故障重试，少量重试可能在旧槽到期前耗尽。这与“请求真正发出后供应商失败”不同。

## 槽位和持久队列

Redis Lua 仍原子清理到期成员并决定是否准入，但整个键的 TTL 现在取所有成员中**最晚到期时间再加 60 秒**，不能被后来的短调用缩短。并发上限没有增大，也不提前删除失联请求的槽；无法确认远端是否停止时保留保守租约。

`MODEL_BUSY` 在网络请求与 Token 预留之前发生。Worker 把它记录为容量等待，保留同一任务、请求号与图检查点，1–5 秒后再尝试；`attempts` 不因这次拒绝增加，另以 `capacity_deferrals` 记录等待次数。已发生的 HTTP、Token 与操作总预算继续累计，包括之前的检索重排和在途未知调用，不因等待或手动重试重置。真正的供应商故障仍按原重试次数和退避处理。

默认 `WORKER_CAPACITY_WAIT_SECONDS=900`，允许配置 30–3600 秒。窗口从本段容量等待第一次发生时计算并持久保存，跨 Worker 重启有效；到期后转为失败并释放任务的逻辑执行预留，不再启动 Agent。成功或转入其他故障处理时结束该等待段。等待不会无限延长，也不占着 SQL 事务休眠；它仍占用全局/空间排队名额与执行预留，队列满时其他新提交仍可能被拒绝。

网页显示“助手繁忙，任务已排队等待”，可随时取消。到期后允许用户手动重试；该操作重置故障尝试/容量等待元数据并重新进行任务准入，保留历史模型用量和单请求累计预算。OCR 等直接 HTTP 调用不会假装进入后台队列，繁忙时正常返回 503 和 `Retry-After`，由用户稍后重试。

## 未知用量与运维

未知供应商结果不会标记免费。调用创建超过 `2 × max(Agent 超时, 模型超时) + 120 秒` 后，Worker 每分钟维护按原预留保守结算为 `uncertain`；真实有效供应商用量仍按已报告值结算。模型槽自然过期与费用清算是两个独立期限。

受保护的 `/api/ops/status` 的 `queues` 新增：

- `model_slots`：当前未到期槽数、配置上限及最近到期秒数；不输出槽 token 或用户信息。
- `model_reservations`：未结算数量、最旧年龄及清算阈值。
- `capacity_waiting_jobs`：目前等待模型资源的队列任务数。

预留年龄超过清算阈值再加 120 秒时产生 `MODEL_RESERVATION_STALE` 本地告警，提示检查 Worker 维护或账本积压。状态里仍有预留并不自动等于泄漏，须结合年龄判断。没有接入外部通知。
