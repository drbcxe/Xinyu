# HTTP、任务与 Agent 链路的本地容量探测

本探测补充纯检索耗时，实际运行独立 API 和 Worker 进程，经本机 TCP HTTP、访客 Cookie、授权检查、Redis 限流/模型槽、PostgreSQL 队列及同步 LangGraph 检查点，执行本地 BGE、Qdrant/BM25/RRF、重排、工具及引用校验，最后通过 HTTP 读取保存结果。

生成模型使用本地确定性 OpenAI 协议服务：固定 150 ms 基础延时，输出工具调用、合法引用 JSON 和可控 503/401/坏格式；重排固定保留前八项。它验证协议、资源控制与故障路径，不代表 GLM 平台性能、Token 计数准确性或沟通建议质量，也不消耗付费模型额度。已有真实模型质量证据见 [Agent 评测](./agent-evaluation.md)。

```powershell
Set-Location -LiteralPath 'D:\Study\简历\Xinyu'
$env:PYTHONUTF8 = '1'
.\.venv\Scripts\python.exe -m scripts.benchmark_pipeline --steady 24
```

要求本地 PostgreSQL/Redis/Qdrant 已启动、本地 Embedding 已缓存；不下载模型，不安装依赖。使用随机 `xinyu_eval_*` 数据库和向量集合，以及专用且必须为空的 Redis DB 14（可用 `XINYU_EVAL_REDIS_URL` 选择其他空库）。沿用真实 D 盘 Embedding 缓存；运行日志、删除恢复记录/密钥和上传临时目录单独放在 `.runtime/benchmarks/probe-*`，退出后清理。本地业务库、科研归档及已有账号不参与测试。早期开发探测曾向共用恢复日志追加合成空间的保留意图，未改写原记录或业务内容；当前运行包装已隔离该写入。

仅支持本机基础服务。脚本拒绝已有数据库/向量集合和非空 Redis，API 使用临时端口。结束时核对并停止自己启动的进程树，再移除临时库、集合与运行目录；不会停止平时开发的 8000/5173 服务。强制杀掉探测主进程仍可能留下随机资源，应按该次运行的准确名称核对处理，不可直接清空共享 Redis 或模糊删除数据库。

| 条件 | 设定与口径 |
| --- | --- |
| 合成资料 | 12 个独立访客、每空间 8 份聊天，包含不同主题；所有成功任务必须实际使用资料、执行 `search_chat_history` 并完成 hybrid + rerank |
| 初始突发 | Worker 起初停止，8 个客户端线程提交 16 次，队列上限临时设为 8；保留拒绝样本，随后启动真实 Worker 消化积压 |
| 稳定并发 | 4 个闭环客户端提交 24 次，包含实际 429 拒绝，不只报告成功请求 |
| 默认保留的控制 | 每 IP 20 次/60 秒、每空间最多 2 个待处理任务、访客每日 8 次；Worker 并发 2、模型槽 4 |
| 为缩短故障演练调整 | Worker 租约 15 秒（平时 90 秒）、Agent 预算 60 秒（平时 300 秒）、模型请求超时 10 秒（平时 60 秒）、外层重试基数 1 秒（平时 5 秒） |
| 故障 | 一次 503 后正常；401 和持续坏格式；重放相同请求；取消在途请求；杀掉有在途调用的 Worker 再启动 |
| 延迟 | 提交 HTTP、任务 HTTP 轮询，以及提交前到取到终态结果的耗时；轮询间隔 200 ms，包含观察延迟。单个故障只有 1 个样本，不具有分位数统计意义 |
| 内存和队列 | 以 100 ms 等待间隔采样 API/Worker 进程树 RSS、SQL queued/running 和 Redis 模型槽；采样查询有额外开销，可能漏峰值。RSS 不含探测驱动、数据库/Qdrant、Docker 与 OS 缓存 |

故障阶段遇到每 IP 限流，会记录拒绝和 `Retry-After`，真实等到窗口恢复后再检查故障，等待单独记录，不能隐藏为快速成功。突发包含首次 Worker/Embedding/缓存准备，稳定阶段仍有多空间缓存变化，不能用热查询单值替代完整响应时间。

Worker 被强制终止时，在途请求的供应商结果可能未知。旧模型槽保留到租约失效；未结算用量等待保守清算，不能为了让压测结束时显示零而删除。报告保留结束时的槽位和账本状态。这会在崩溃后暂时降低容量，须与任务恢复耗时区分。数据库逻辑执行预留应随终态释放，不应与未知模型费用预留混为一谈。

模型槽租期按 `max(30 秒, 当前调用剩余执行期限 + 模型超时 + 30 秒)` 设置；未知费用预留在创建超过 `2 × max(Agent 超时, 模型超时) + 120 秒` 后，由 Worker 每分钟维护保守结算。任务恢复成功不代表这两种预留已立即归零；本轮没有等到保守结算截止，结束时记录了剩余状态，不能宣称已实测崩溃后的全部容量恢复。极低模型并发配置下，这个保守窗口对可用性影响仍需后续补充验收。

## 2026-10-28 本机结果

完整聚合记录及源码/脚本指纹见 [pipeline-benchmark.json](./pipeline-benchmark.json)。记录生成时 Git 基线为 `700eb74`，工作区含本探测的新文件，`git_worktree_dirty=true`；文件指纹标识实际测量实现。Windows 11，Python 3.12.15，24 个逻辑 CPU，15.74 GiB 内存，PostgreSQL 18.6；机器仍运行普通开发服务，没有并行运行回归套件或其他评测。

| 阶段 | 提交 / 接受 / 拒绝 | 全部提交 HTTP P50 / P95 | 成功任务端到端 P50 / P95 | 任务轮询 HTTP P95 |
| --- | --- | --- | --- | --- |
| 停 Worker 后突发，再启动消费 | 16 / 8 / 8（队列满） | 181.6 / 335.9 ms | 8.18 / 11.21 s（8 个） | 39.3 ms |
| 四个闭环客户端 | 24 / 12 / 12（每 IP 限流） | 48.6 / 133.6 ms | 4.01 / 4.11 s（12 个） | 29.8 ms |

提交时长同时包含成功和快速拒绝，不能用其较小的中位数声称成功任务也只需几十毫秒。观察到最多 8 个排队、2 个执行中任务、2 个模型槽；API/Worker 进程树 RSS 合计采样峰值 628.09 MiB，RSS 可能重复计算共享页。它不包含 Docker 服务和驱动内存，也不是应用内存硬上限。

故障阶段实际等待一次 37 秒的 IP 限流窗口，再执行断言：503 单次重试后成功；401 与持续坏 JSON 各终态失败且仅 1 次 Worker 尝试；相同请求重放返回同一任务且额外模型调用为 0；跨空间读取任务/资料均返回 404；取消后迟到结果为 0。运行中的 Worker 被终止后，任务在第 2 次执行成功，观察用时 21.58 秒，使用本探测的 15 秒任务租约。

结束时保存 22 条成功结果，模型调用账本为 94 completed、1 rejected、2 uncertain、1 reserved，仍有 1 个旧模型槽；这些是本地假供应商协议记录。数据库逻辑执行预留为 0，已用约 10.70 MB，其中图状态约 10.12 MB，说明图持久化也需容量与保留约束。独立进程树、数据库、向量集合、Redis 键和私有运行目录已清理；没有为“清零”提前取消未知供应商预留。

本结果属于小规模本机观测，不是最大并发、持续吞吐、生产 SLA 或真实模型延迟承诺。队列、空间/全局存储、每日额度可能先于 CPU 饱和而拒绝请求，拒绝是有效结果。生产还需要服务卷/WAL/Qdrant/Docker 的容量安排、真实供应商限流与延迟、持续到达模型、长时稳态和目标机器上的验收。
