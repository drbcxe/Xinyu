# 检索复用与本机性能边界

本文记录 E11 中分块/BM25 复用、引用校验合并与本地测量的结果。后续已补充数据库逻辑预算、向量准入和受管运行文件预算，进度见文末；这些控制仍不能当作整个文件系统的物理硬配额。

## 检索路径

每次查询先读取当前空间的资料 ID、版本、类型与创建时间；命中缓存时复用分块和 BM25 词频结构，不重读全部原文。缓存键隔离数据库、空间、资料类型、分块签名与版本集合。不同查询复用同一份语料结构，不缓存用户问题或生成回答。

修改、删除或状态改变通过版本集合使其他进程的旧缓存失效；本进程写入还会主动失效。无论是否命中缓存，返回片段前都按当前空间批量读取 SQL 来源，再逐条检查版本、偏移和原文。LangGraph 也复用这一批量校验。缓存不会替代权限与来源校验，数据库不可用时不直接把旧缓存当作有效资料返回。

旧路径会在 12,000 个分块后静默丢弃较早语料；现已移除这个截断。大语料在不能缓存时仍完整参与关键词检索，不能通过缩小检索范围制造更好的耗时。

## 缓存的资源约束

| 项目 | 默认值及含义 |
| --- | --- |
| `RAG_CACHE_BYTES` | 每进程 64 MiB 估算记账预算，不等同于进程 RSS 上限 |
| `RAG_CACHE_ENTRIES` | 最多 8 份语料结构，按 LRU 淘汰 |
| `RAG_CACHE_TTL_SECONDS` | 120 秒；API 每 15 秒、Worker 维护轮次清理过期项 |
| 冷构建并发 | 每进程最多 2 个，不同请求等待构建槽最多 3 秒，繁忙返回 `RAG_BUSY` |
| 同语料并发 | 共用同一次在途构建；失效时禁止旧构建重新发布到缓存 |
| 超出缓存预算的语料 | 本次完整构建与查询，不常驻缓存；仍可能有明显 CPU 和峰值内存开销 |

API 与 Worker 是独立进程，分别有缓存预算。Python 分配器、模型运行时和临时构建内存不包含在“缓存估算字节”中；不能承诺整个进程只用 64 MiB。运维接口的 `retrieval_cache` 和 `xinyu_rag_cache_*` 指标只表示调用该接口的进程，不代表所有 Worker 的合计。

## 可复现测量

```powershell
Set-Location -LiteralPath 'D:\Study\简历\Xinyu'
$env:PYTHONUTF8 = '1'
.\.venv\Scripts\python.exe -m scripts.benchmark_retrieval --repetitions 9 --max-mib 8
```

脚本使用随机独立 PostgreSQL/Qdrant 空间和专用空 Redis DB，生成 20/100/300 份合成聊天。测量 BM25 + SQL 的无复用、允许缓存、同空间及双空间四并发；最后清理隔离资源。没有调用生成模型、重排或 Embedding，不是完整 HTTP/Agent 响应时间或质量分数。

允许缓存的九次测量包含第一次冷构建，因此 P95 会反映冷启动；不能只取热查询宣称整体 P95。前三条结果的 ID/原文排序在重复查询和有无缓存时必须一致。RSS 以 psutil 每 25 ms 采样，包含共享/原生内存，可能漏掉极短峰值。全局 OS 环境未隔离；正式记录应在本轮回归和其他评测结束后单独运行，避免并行测试干扰 CPU。

本轮实测汇总与环境信息见 [retrieval-benchmark.json](./retrieval-benchmark.json)。这里只报告该合成分布、本机与样本量的观测，不推断生产并发容量。大文件、词汇分布、CPU、数据库网络和冷 Embedding 都会改变结果；正式部署还需单独验证整个 HTTP、队列与真实模型链路。

Windows 11、24 个逻辑 CPU、15.74 GiB 内存的最终独立运行结果如下。每阶段 9 次查询，缓存阶段包含一次冷构建；两空间并发为 4 个线程共 8 次请求，均完成。

| 合成资料 | 无复用 P50 | 允许缓存 P50 | 允许缓存 P95（含冷构建） | 两空间并发 P95 | 两空间并发采样峰值 RSS |
| --- | --- | --- | --- | --- | --- |
| 20 份 / 约 0.25 MiB | 109.0 ms | 9.4 ms | 94.0 ms | 144.6 ms | 209.6 MiB |
| 100 份 / 约 1.99 MiB | 657.2 ms | 10.6 ms | 597.1 ms | 1,259.0 ms | 284.0 MiB |
| 300 份 / 约 7.99 MiB | 2,599.9 ms | 2,551.2 ms | 2,714.7 ms | 5,125.6 ms | 539.7 MiB |

约 8 MiB 的语料超过默认缓存估算预算，未常驻，所以没有明显热缓存收益；跨空间冷构建也会竞争 CPU。两空间各约 2 MiB 的缓存合计超过单进程 64 MiB 估算预算，会发生 LRU 淘汰，因此并发尾延迟明显高于单空间热查询。不能拿单空间约 10 ms 中位数宣称所有查询或多用户都能达到该耗时。

107 项回归已通过，包括真实向量库的删除/并发修改失效、缓存合并/淘汰/过期、跨空间隔离、批量来源校验与超过旧截断边界的检索。固定 50 案例的无生成模型检索回归另行运行，只比较 13 条有证据标注的检索指标，不把性能提升当成语义质量提升。

## 完整容量边界的进度

本轮已完成业务行/图状态/元数据的数据库原子预算、执行预留、取消/删除释放、永久错误停止、旧行迁移回填和恢复核对，见 [storage-budget.md](./storage-budget.md)。下列整体要求仍保留作为审计依据：

- 所有对话/result、任务 payload、反馈、账号/验证/提醒元数据与图检查点都纳入空间和全局预算，取消、删除、覆盖与过期及时释放。
- 并发写入与图保存共用原子预算，不能“先检查再无保护写入”；任务入队为执行和最终结果留出空间，避免调用模型后才发现无处保存。
- 处理拒绝时保持结构化错误与可恢复状态，永久容量错误不得反复自动调用模型；已存在数据不能因为迁移被丢掉。
- 限制匿名空间与账号元数据的增长，区分逻辑内容字节、向量估算、数据库物理文件、日志/备份和 D 盘剩余空间。
- 验证真实图保存、并发配额、失败回滚、删除释放、迁移回填、备份恢复和界面用量展示；再审计 E01/E11，不能仅用缓存测试宣布全部完成。

向量点位准入预算与故障清理已补充，见 [vector-capacity.md](./vector-capacity.md)；日志/备份/恢复明文的写前预算及磁盘空闲拒绝已完成并验收，见 [runtime-file-budgets.md](./runtime-file-budgets.md)。真实 HTTP/队列/LangGraph/混合检索配本地模型协议服务的小规模并发及故障实测见 [pipeline-performance.md](./pipeline-performance.md)。PG/WAL/Qdrant/Docker 服务卷物理边界、低并发崩溃后的全部容量恢复、长时负载及真实供应商性能仍待后续验收，未把局部数据库或文件预算标成全部容量工作完成。
