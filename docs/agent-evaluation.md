# Agent 质量评测

## 范围

`quality/cases.json` 固定了 50 个中文合成案例，10 类场景各 5 个：日常沟通、分歧、边界、保存前确认、提醒、约会、检索、记忆更新、多轮记忆和提示注入/空间隔离。开发集 30 个，预留集 20 个；预留集不能用于调整提示词后反复刷分。固定业务时间为 `2026-10-27T12:00:00Z`。这些是本项目领域案例，没有运行官方 LongMemEval 数据集，不能宣称取得其基准分数。

只有 **13 个案例含明确的检索片段标注**。其余案例评估行为或生成质量，不计入检索均值。每次加入 32 条合成干扰偏好和另一个空间的标记资料。更新和删除案例保留过期向量，让 SQL 所有者、版本与原文校验阻止陈旧引用。多轮案例确认保存偏好后插入填充对话，避免只依靠最近四轮窗口答对。

## 独立数据与运行边界

每次创建随机 `xinyu_eval_<16位十六进制>` PostgreSQL 数据库及同名 Qdrant 集合，迁移后再写入合成资料。默认 Redis DB 14 必须为空，否则拒绝启动；不会清空已有 Redis DB。资源通过退出栈清理，报告记录清理是否完成。意外终止的运行不会被记为完成，应先核实该次资源的归属再处理，不得批量删除其他数据库或集合。

评测不读取线上咨询、账号内容或用户反馈，不上传 LangSmith Trace。Embedding 只使用 D 盘已下载模型。业务库和原科研文件夹不参与评测。运行报告在忽略的 `.runtime/evaluations/<run_id>/`；默认不提交原文或模型回答，公开结果只保留汇总。

`--mode retrieval` 不调用生成模型，比较 BM25 和本地 BGE + BM25/RRF 的前三个片段；该预览关闭模型重排。`--mode live` 执行真实 LangGraph，包括其生产配置的重排、工具循环和结构校验。两者衡量的范围不同。

## 如何运行

先运行 Docker 中的 PostgreSQL、Redis、Qdrant，确认 D 盘 Embedding 已准备好。在项目根目录执行：

```powershell
$env:PYTHONUTF8 = '1'
.\.venv\Scripts\python.exe -m quality.run --mode retrieval --split all
.\.venv\Scripts\python.exe -m quality.run --mode live --split dev --judge --token-budget 200000
# 开发修复冻结后再执行预留集
.\.venv\Scripts\python.exe -m quality.run --mode live --split holdout --judge --token-budget 200000
# 单案例排查会保留为独立小范围结果，不冒充全量验收
.\.venv\Scripts\python.exe -m quality.run --mode live --split dev --case conflict-02 --token-budget 20000
.\.venv\Scripts\python.exe -m quality.compare <baseline-report.json> <candidate-report.json>
```

真实模型运行使用本地 `.env` 的模型服务，会消耗额度。每次运行设置全局 Token 上限，所有实际模型请求、重试、重排和可选评审均通过同一账本记账。未报告用量的调用按保守预留结算；没有可靠单价时不编造人民币费用。超出预算后剩余案例标为未运行，命令返回非零；不是自动缩小分母。

需要同时运行独立评测时，显式设置 `XINYU_EVAL_REDIS_URL` 为另一个专用空 DB；不得指向业务 Redis DB。日常使用顺序运行即可。

## 指标如何理解

- **完成率**：成功生成案例 / 请求案例。模型报错仍留在分母中。
- **端到端规则通过率**：成功完成且所有规则通过 / 请求案例；另报告已完成案例的条件通过率，避免掩盖失败。
- **规则**：结构有效、无其他空间标记泄漏、工具在允许列表、候选引用来自当前用户输入、没有特定形式的虚假代发/预订声明、执行预算有限、没有隐式保存、引用仍有效。字符串规则只是定向探针，不能证明所有语义安全问题都不存在。
- **工具轨迹**：使用 `agentevals` 的 `superset` 轨迹匹配。要求必要工具成功调用，允许额外的合法工具；自然语言查询参数不做字面匹配，参数类型、额外字段及当前空间权限由业务校验和独立集成回归覆盖。没有必要工具的案例记为未评估，不计为通过。
- **检索**：必须同时匹配资料 ID 和标注片段，不能仅命中文档就算正确；去重相关证据。Recall 为找回证据占比；Precision 为返回的前三个片段中相关片段比例（返回不足三条时按实际条数计算）；MRR 为首个相关片段倒数排名；nDCG 使用二值相关性和对数折损。当前 13 个标注案例均为一条目标证据。
- **模型评审**：理解问题、依据资料、尊重双方、可行动且不过度承诺，各 0–2 分。使用相同 GLM 作为评审时存在同源偏好，只作辅助；单独展示评分覆盖，不能替代人工抽查或确定性规则，也没有一个混合总分。

报告记录数据 SHA-256、应用/评测 Python 源码 SHA-256、Git 提交、工作区是否有未提交修改、包版本、模型名和 Token。只有数据版本、拆分、模式和案例集合相同且资源已清理的完整尝试才可比较；未运行案例会拒绝比较。已有错误案例可比较完成率的改善。

## 回归与已经发现的问题

CI 执行纯评分器及真实 PostgreSQL/Redis/Qdrant 集成回归；用确定性向量和模型替身验证隔离、删除重试和任务恢复，不消耗模型 Key，不把这些结果当作语义效果分。

首轮开发集真实模型完成 29/30，`conflict-02` 因返回四条回复超过三条约束而失败。原修复提示过于笼统，反复消耗八次调用。现已明确输出上限，反馈具体字段错误，格式修复限制为两次；耗尽或协议过期的检查点在人工重试时重建，鉴权/格式等永久错误不再由 Worker 连续自动重试。单案例复跑已完成；全量修复后结果以汇总报告为准。

首次 50 案例检索预览的 13 条标注中，混合检索 Recall@3 为 0.615，BM25 为 0.462；混合检索 Precision 为 0.372，BM25 为 0.423。召回提升伴随噪声增加，这不是质量全部达标的证明，后续检索优化必须同时观察召回、精度和延迟。

参考：[AgentEvals](https://github.com/langchain-ai/agentevals)、[LongMemEval](https://github.com/xiaowu0162/LongMemEval)。本项目只集成 AgentEvals 的轨迹评分器，并参考长期记忆评测维度；没有声称运行 Ragas 或上述官方完整基准。
