**三、浏览器与服务连接**

开发：浏览器 http://localhost:5173 → Vite /api 代理 → http://127.0.0.1:8000。前端请求统一写 /api 相对路径，携带 credentials: include。

宿主机后端：PostgreSQL/Redis 地址分别 localhost:5432、localhost:6379。容器内部用 postgres:5432、redis:6379，不能继续写 localhost。

生产构建：admin-ui/dist 复制进 API 镜像；FastAPI 托管静态文件，根路径显示界面，所有 API 保留 /api 前缀；本地访问 http://localhost:8000。容器仅在需要时暴露 127.0.0.1 端口。

前端使用 BrowserRouter：`/projects` 项目列表、`/projects/new` 创建、`/projects/:projectId` 工作台、`/projects/:projectId/files` 文件管理、`/projects/:projectId/files/:artifactId` 实验详情、`/projects/:projectId/comparisons?artifact=...` 比较、`/overview` 系统概览。项目范围由网址确定；切换项目/文件时取消旧请求并清除旧范围显示。生产托管需为这些前端地址提供 index.html 回退，不能将 `/api` 错误或缺失静态资源伪装成 HTML 成功响应。

Celery worker 和 beat 在 Linux 容器中运行，beat 只启动一个实例。[Celery 平台说明](https://docs.celeryq.dev/en/stable/faq.html)

**四、数据对象先控制在闭环需要的范围**

- Project：id 为 P001 这类受限字符串、name、description、created_at。项目代码创建后不修改。
- Artifact：UUID、project_id、original_name、sha256、受控 storage_key、created_at。文件内容不可变；相同项目和 hash 重传复用记录。
- ExperimentRun：UUID、project_id、artifact_id、run_id（R001 标签）及 CSV 必需字段。唯一性为 artifact_id＋run_id；允许不同版本文件出现相同标签。
- Thread：UUID、project_id、title、active_run_id。Graph 的 thread_id 使用本对象 ID，后端检查项目归属。
- Message：UUID、thread_id、role、content、client_message_id、created_at。
- AgentRun：UUID、thread_id、request_id、status、result、error、lease_until、attempt_count、created_at、updated_at。
- RunEvent：run_id、递增 sequence、type、payload、created_at；唯一键 run_id＋sequence。
- Memory：UUID、scope、project_id、key、value、source_message_id、revision、is_active、supersedes_id。
- TodoTask：UUID、project_id、title、status（todo/done/cancelled）、source_message_id、revision。
- Reminder：UUID、task_id、due_at、timezone、revision、status（scheduled/completed/cancelled/expired）。
- Delivery/Outbox：事件 ID、reminder_id、revision、payload、status、attempt_count。Notification 使用唯一 event_id；is_read 独立记录。

待办完成是用户动作；AgentRun 成功表示一次程序执行成功，两者不能共用一套“完成”判断。

所有时间使用带时区时间戳，数据库存 UTC，界面按 Asia/Shanghai 展示。用户“明天九点”的解析使用服务器注入的当地日期与时区，并在登记结果中显示确定时刻。

POST runs 在 Day 3 可以先在同步 def 路由里执行 graph，再返回 201 与最终状态；Day 5 改为登记后入队返回 201 queued。前端从 Day 3 起都按 run_id 查询最终状态，因此数据契约不变。201 表示执行资源已创建，不代表已执行成功。

当前已实现：GET messages 返回 {items,active_run_id,runs}，items 为最近 60 条消息，runs 包含各轮状态、模型名、事件、真实 usage（如供应商提供）和比较证据。聊天页在同步 POST 尚未返回时轮询该接口更新真实进度；GET run 仍可按 ID 独立读取状态。/projects/:projectId/chat 使用 thread 和 artifact 查询参数定位会话/文件。图状态位于独立 agent_checkpoints schema；业务表与 checkpointer 分别初始化。

CSV 第一版只支持同一 artifact 内比较；跨文件版本的同名 run 必须先让用户选文件。本版不做静默拼接。

比较复用已有 Decimal 计算工具；计算所用原文件 SHA256 必须与 Artifact 记录一致。成功结果与来源存入 comparisons 表，provenance 只暴露原文件名、SHA256 和评估条件，不暴露宿主机绝对路径。INCOMPARABLE_RUNS 的 details 为字段到 {baseline,candidate} 的映射；前端逐项展示差异。相对改善率在基线不大于零时为 null。历史结果为当时保存的快照。

**六、图与工具**

当前偏好模块已实现四个 key：default_baseline、preferred_metric、response_length、report_language。revise_memory 验证来源为当前真实用户消息；generation 每次模型调用前加载数据库最新生效偏好，get_project_preferences 的停用项只返回 key/revision/is_active 和空值。登录、模型检测与 resume 路由仍属于后续计划。

IncomingGraphState 规划包含 messages、project_id、thread_id、run_id、artifact_id、selected_run_ids、active_memories、tool_steps、evidence、pending_input、error。当前项目范围、run/request ID 从可信请求上下文注入，不相信模型自行给出的范围；生效偏好直接在每次调用模型前读取，不缓存为可过时的图状态。

主图：context_loading → generation（模型/工具有界循环）→ save_conversation → 条件记忆更新 → finalize。显式信息缺失通过 interrupt 持久化等待，由 resume 恢复；保持 tool_call 与 ToolMessage 配对完整。

首版工具：get_project_context、list_runs、compare_runs、revise_memory、create_task、update_task、create_followup、update_followup、cancel_followup、get_task_status。工具使用服务层，同样校验范围、版本和参数。比较包装器用 artifact_id 查受控路径，再调用已有 compare_runs，模型不提交宿主文件路径。

create_task(title,details) 创建 TodoTask；update_task(task_id,status,expected_revision) 只修改用户待办的 todo/done/cancelled。create_followup(task_id,due_at,timezone) 为已有待办登记提醒；一句话同时要求待办和提醒时先建待办再登记。get_task_status 查询 TodoTask 及关联提醒；AgentRun 的执行状态通过 run 接口和可信会话上下文读取，模型不能把程序执行状态改成成功。

最多 6 次工具调用、暂时性错误最多重试 2 次；工具业务拒绝作为结构化结果回传模型，系统异常写入真实错误状态。对同一 thread 同时提交的第二次执行返回 THREAD_BUSY，界面等待，避免两个进程改同一 checkpoint。

模型与业务库先采用同步调用，Day 5 同步 graph.invoke 在 Linux worker 中执行；每次执行独立管理 DB session/checkpointer 连接，避免跨线程或跨进程共享 session。

LangGraph checkpointer 管会话图状态，Memory/TodoTask/Artifact 是独立业务表。持久化恢复与外部副作用的重复处理分别实现。[持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[中断恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)

**七、后台与主动流程**

AgentRun：queued → running → needs_input / succeeded / failed；queued 可取消。运行中终止、GPU 训练取消留待专业工具阶段，不设置无效按钮。

Day 5 使用 Redis 作 Celery broker，数据库作事实来源：先写 AgentRun 与 Outbox 再提交，单 beat 每 15 秒扫描未分发事件/到期提醒；投递可能重复，因此 worker 校验状态、租约与动作键。同一 run 内写入副作用用 run_id＋tool_call_id 去重。

租约到期时检查 worker/task 信息，再按预算重新入队或置 failed；执行恢复策略和实际运行记录必须可查。超过预算不会无限挂在 running。重复生成可能增加模型调用费用，不能声称模型调用本身 exactly-once。

主动图：加载待办 → 核对提醒当前 revision/任务状态 → 结合事实生成通知（模型失败使用事实模板）→ 事务写 Notification 和交付记录 → 标记处理结果。站内事件唯一键 reminder_id＋revision；重复事件不产生第二条通知。

一周默认：到期后 24 小时内补发，超过 24 小时标 expired 并显示原因。任务 done/cancelled 或提醒已取消时不再发送。改期递增 revision，旧事件丢弃并保留处理原因。

**八、事件协议**

每条 SSE 消息包含 id: sequence、event: 类型、data: JSON，并以空行结束。payload 至少有 run_id、sequence、type、created_at；支持 run.started、context.loaded、tool.started、tool.finished、input.required、reply.completed、run.failed 和 heartbeat。

v0.1 必须实时显示业务步骤和最终答复；逐 token 的 reply.delta 在 SDK 支持且测试通过时接入，不承诺所有模型都流式输出。前端收到终态主动关闭 EventSource。刷新从 after 或 Last-Event-ID 续读，按 sequence 去重；事件传输失败后仍用 GET run 核对事实。

自建 FastAPI 事件协议用原生 EventSource/fetch 对接，前端 SDK 只有确认兼容其服务协议后再采用。

**九、事务与文件边界**

上传最大 5 MiB，1—10000 条实验记录，UTF-8/UTF-8 BOM，规范化 CSV；原始字节保存在 .runtime/artifacts，应用生成 storage_key，multipart 临时目录为 .runtime/upload-tmp。同项目按原始内容 SHA256 去重。先校验全文件再事务插入；失败不留下部分 ExperimentRun。run/Artifact 的 p 必须一致，不能仅凭文件名找数据。文件和数据库是两个存储系统；提交结果不明确时保留原文件，避免误删已提交记录的来源。

数据库迁移用 Alembic，LangGraph 组件自己的初始化按锁定版本文档执行，两套表都在干净数据库上验证。应用 API 启动前先运行迁移，worker/beat 随后启动。schema 升级与镜像回退有独立说明。
